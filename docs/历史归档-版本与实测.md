### Bug 记录：称呼错乱（2026-10-05 晚，已修复）

- **现象**：AI 坚持叫用户"阿灿"，聊天中纠正为"小徐"后，冒泡时又叫回"阿灿"，甚至虚构"你之前说的，我记性好着呢"
- **根因**：profile.md 残留开发测试脏数据（称呼：阿灿），每轮对话都注入 prompt；聊天纠正只存在最近 10 轮上下文，冒泡新开上下文时丢失，脏数据重新生效
- **修复**：①清除 profile.md 脏数据（称呼：小徐）②新增**事实便签**机制（/note /notes /forget）：用户亲口告知的持久事实存数据库、注入 prompt，优先级标记为"与旧信息冲突时以此为准"③确立信息优先级：事实便签 > profile.md > 聊天上下文
- **结论**：这是记忆系统缺失的典型症状，事实便签是 v0.5 过渡方案，自动从聊天提取事实仍属记忆系统 P1
- **附带好评**：用户反馈"除了这个（称呼问题），冒泡机制都挺不错的"——冒泡触发时机、颜文字使用、对话语感均通过实测

### 实测反馈记录 #4（2026-10-07，项目消息 @听深深的话ミ；当日中午按用户指正修正）

**Bug：记忆提取跨轮错位归因 + 视角错乱（✅ 2026-10-07 已修复）**

- **现场**（按发言时序）：
  1. 11:30 小葵："乖！那现在先去吃个午饭，别饿着，下午晒晒太阳，晚上好睡～" → 记下 `(计划|健康作息) 小徐答应今晚11点按时上床睡觉`

### 实测反馈记录 #16（2026-10-09，代码 ↔ 需求对齐回归）

**背景**：以「需求概要 v0.30」为准逐条核对代码，找出"文档说一套、代码做一套"的地方并修。以下是这次真正踩到的坑。

**坑①：`BUSY_SIGNALS` 漏一个逗号，"安静"从未生效**

- 现象：corpus 里写的是 `"别说", "不要说" "安静", "stop"`——`"不要说"` 和 `"安静"` 之间**漏了逗号**，Python 的隐式字符串拼接把它们粘成了 `"不要说安静"`。结果"安静"这个忙碌信号从来没被识别过，用户说"安静"不会进静默期。

**坑②：随机闲聊时段用的是全局作息，与"按人格作息自适应"结论冲突**

- 现象：待确认 #8 的结论是"按人格作息自适应（人格池已有各自作息 + 频率倍率，全局固定会打架）"，代码里 `wake`/`sleep` 两个定时任务确实跟人格走了，但**随机闲聊 `random_chat` 还用 `config.WAKE_HOUR`-`config.SLEEP_HOUR` 全局值**。夜猫子（10 点起、凌晨 2 点睡）会在 8–10 点、22–23 点这些它本该在睡觉的时段被发起闲聊。
- 修：`scheduler._awake_hours(wake, sleep)` 统一按时段生成 cron，**跨午夜拆成两段**（"10-23,0-1"）。顺带修了 `sleep_hour=0`（0 点睡）被当成"睡 0 小时"的边界——按 24 点处理。

**坑③：群聊砍了半年，代码里还有一堆残留**

- v0.27 就删了 `groupchat.py`，但通道层 `send(text, sender="")` / `typing(sender="")` 还留着"群聊模式：带上发言人名字"的分支和注释；日记复盘 prompt 还写着"可能只和一个人，也可能和一群人"；记忆提取 prompt 里举例还是"群里聊了 X"；`.gitignore` 还留着 `group_session.json`。
- 教训：**删功能只删主文件是不够的**，接口签名/prompt 措辞/配置文件里的残留会一直误导后来的人（也包括 AI）。这次一并清干净，并加了签名断言防复发。

**结论**：本文档（需求）与代码的偏差主要来自两类——①新决策落地时只改了入口没改全部分支（作息）；②砍功能时只删主文件没清残留（群聊）。后续建议每次拍板后按 `AGENTS.md` 的对照表过一遍。


### 实测反馈记录 #17（2026-10-09，工作系统落地踩坑）

**背景**：S3 主线第①②项落地——工作系统（`work.py`）+ 紧急联系触发语义。以下是这次踩到的坑与设计取舍。

**坑①：内部 prompt 调完整人设 → 与工作状态注入互相递归爆栈**

- 现象：工作单元结算时要生成 1 条"可分享素材"，prompt 里用了 `persona.build_system_prompt("AWAKE")`；而 `build_system_prompt` 里又注入了「手头的事」= `work.prompt_hint()` → `status()` → 结算 → 生成素材 → `build_system_prompt`……无限递归，`RecursionError` 直接崩。
- 修：抽出 `persona.core_identity_prompt()`（通用规则 + 名字 + 人格，**不含**任何会反过来再调它的动态段）供内部 prompt 使用；`build_system_prompt` 改为复用它。
- 教训：**任何"内部 LLM 调用"都不要拼完整 system prompt**。完整人设里塞的动态段（时间、状态、手头的事）越来越多，只要其中一个会触发新的 LLM 调用就成环。内部 prompt 一律用 `core_identity_prompt()`。

**坑②：状态持久化后，测试里把时间往回调是无效的**

- 现象：测试先断言"单元结束会结算（进度 +1）"，再回头断言"此刻处于心流期"——但结算进度已经写进库了，把 `now` 调回单元刚开始也回不到心流期（读到的是"已下班"）。
- 修：顺序调整为"先测心流期/HUD（趁它还在忙），再测结算"，需要重来就 `work.reset()`。
- 教训：**惰性推算的状态机，时间是单向的**——测试要按时间推进顺序写断言，不能回头。

**设计取舍①：为什么是"惰性结算"而不是定时任务结算**

自用阶段服务端跑本机，电脑随时会休眠/关机。如果结算靠定时任务，睡过去的那几个小时就永远丢账（它会"明明忙了一整天却一件没完成"）。改成状态由"现在几点"推算、补账在每次读取时补齐，睡醒回来能一次性把错过的单元全补上（测试里有这条回归）。

**设计取舍②：紧急判定必须保守**

`URGENT_QUERY` 只认明确紧急语义（"急事/出事了/十万火急/在线等"），不认"我急死了""着急""快点啦"。理由：紧急通道是打断成本的**安全阀**，天天被日常夸张说法误触 = 等于没有安全阀。宁可漏判一次（它慢回一条），也不要让"随叫随到"变成常态——那它就没有自己的日子了。窗口默认 10 分钟，过期自动恢复。


### 实测反馈记录 #18（2026-10-09，网页端 Web UI 落地）

**背景**：G 模块自用阶段主载体上线。参考的是之前那版"有生活的朋友 · 原型 Demo"——**原型的机制是前端模拟的**（虚拟时钟、台词池），这次做的是真接后端：同一个 `friend-<id>.db`、同一套记忆/日记/工作系统/调度器，网页只是另一块屏幕。

**坑①：冷启动补账串行调 6 次 LLM，页面被卡住 5.8 秒**

- 现象：`/api/state` 首帧 5.79 秒才返回。查下来是 `work.status()` 在补账——电脑睡了一觉，醒来要补 6 个单元，而每个单元结算都会生成 1 条可分享素材 = 连续 6 次 LLM 请求，全在 HTTP 请求线程里同步跑。
- 修：素材生成改**后台线程 + 同一时刻只排一条**（`_produce_shareable` 只负责排队）。冷启动补账只触发 1 次生成，剩下的由后续单元自然接上（单元间隔几十分钟，不会积压）。改完 0.03 秒。
- 教训：**惰性补账的代价是"补账量不可控"**——补 1 个和补 6 个差一个数量级。凡是在补账路径上做的事，要么够快，要么异步。

**坑②：沙箱/代理环境下请求 127.0.0.1 超时**

- 现象：测试里 `httpx.get("http://127.0.0.1:PORT")` 直接 ReadTimeout，而服务明明活着（GET / 返回 200）。
- 原因：环境里有 `HTTP_PROXY`，httpx 默认 `trust_env=True`，**环境变量代理存在时注册表的 ProxyOverride（`127.*`）被完全忽略**，回环地址也被塞给代理。
- 修：`httpx.Client(trust_env=False)`。已在测试里写死并加了注释——这条不写会让人排查半天。

**设计取舍：为什么是"轮询"而不是 WebSocket/SSE**

自用阶段就一个人用，1 秒一次拉增量消息（`after=lastId`）的开销可以忽略，换来的是：不引第三方框架（只用标准库 `http.server`）、断线重连天然免费（网络恢复后继续拉就行）、服务端无状态更好排查。等真要做多端同步/推送再换 SSE 不迟。

**遗留（已记进需求池）**：开机自启与常驻（电脑重启后得手动 `python main.py web`）、断线重连提示（现在只显示一行"连接断了，重连中…"）、移动端适配。


### 实测反馈记录 #19（2026-10-09，网页端开机自启与常驻）

**背景**：自用阶段服务端跑本机，电脑一重启就得手动 `python main.py web`——那它不是"一直在那儿的朋友"，是"你想起来才去开一下的程序"。所以要两件事：**常驻**（崩了自己起来）+ **开机自启**（重启后自己回来）。

**坑①：`schtasks.exe` 在某些终端里根本不可用**

- 现象：`schtasks /create` 报 `ERROR: The system cannot find the path specified`；进一步测发现**连 `/query` 都是同样的错**，而同一台机器上任务计划服务（Schedule）明明是 Running。
- 判断：不是权限问题，是这个命令行工具在当前会话里不可用。
- 修：改走 Windows 的 `ScheduledTasks` 模块（`Register-ScheduledTask` / `Get-ScheduledTask` / `Unregister-ScheduledTask`），同一套东西、能拿到明确的报错文本。
- 教训：**命令行工具本身也可能是坑**，报错信息（"找不到路径"）会误导你去查路径，实际是工具不可用。写这类外部调用时，把失败原因（stderr）原样带回给用户，别只回一句"失败"。

**坑②：`os.kill(pid, 0)` 在 Windows 上不是探活，是杀人**

- 现象：写"进程还活着吗"时用了 POSIX 惯用法 `os.kill(pid, 0)` 期待"活着不抛错、死了抛 OSError"。
- 真相：CPython 在 Windows 上把 `os.kill` 实现成 **`TerminateProcess(handle, sig)`**——`sig=0` 也会被当成退出码传给 `TerminateProcess`。也就是说这行代码**会直接结束目标进程**。
- 修：改用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess`，退出码 `259`（STILL_ACTIVE）才算活着。
- 教训：**别把 POSIX 语义直接搬到 Windows**。这条如果漏了，后果是"查一下状态"把服务杀了，而且极难排查。

**坑③：vbs 中间层在受限环境跑不起来，改纯 Python 守护**

- 现象：原本设计是 `wscript.exe run_web_daemon.vbs` 当守护（vbs 里循环拉 `main.py web`）。实际跑下来 vbs 进程没起来、日志也没生成，等于整条链路静默失败——**没有任何报错**。
- 修：去掉 vbs 中间层，改成 `daemon.py`（纯 Python 守护）：用 `pythonw.exe` 跑它（无控制台窗口），它再用 `CREATE_NO_WINDOW` 拉起 `main.py web`，输出全部追写到 `logs/web.log`。整条链子无黑框、可观测。
- 教训：**跨语言的中间层（脚本调脚本调脚本）调试成本极高且失败是静默的**。能用同一种语言实现就别绕。

**设计取舍①：为什么必须有 `web.stop` 标志**

守护的目的是"崩了自拉"。但如果没有停止标志，你 kill 一次它起来一次，**永远关不掉**。所以 stop 分两步：写 `web.stop` 标志 + 杀进程；守护每次循环开头和进程退出后都检查标志，看到就退出。想恢复就 `autostart start`（自动清标志）。

**设计取舍②：为什么守护不放在网页进程里自检**

想过让 `webui.py` 自己带 watchdog 线程，但进程真崩了（或 OOM 被杀）内部线程也没了。必须是**外部独立进程**盯着。

**设计取舍③：为什么开机自启有两条路**

计划任务能查状态、能禁能删、不用管理员，是首选；但它依赖 COM，某些环境注册不了。所以兜底写「启动」文件夹（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`）——零依赖、用户自己也能看懂和删掉。两条路都失败时，报错里把两条路的失败原因都列出来，并给手动兜底办法。

**未在本机验证的部分**：装/卸（`autostart on|off`）在受限会话里被拒绝（注册计划任务"拒绝访问"、写启动文件夹 PermissionError），需要用户在自己的普通终端里跑一次 `python main.py autostart on` 生效。测试只覆盖不碰系统的部分（路径一致、启动器内容、探活函数、status 不崩）。


### 实测反馈记录 #20（2026-10-09，网页端操作 UI 化）

**背景**：网页端不能光靠输斜杠命令——换朋友、抽新朋友这种结构性操作在手机/网页上输 `/friend 3` 太反人类，得做成控件；但调试类（带参数、低频）保留输入框。这是"哪些命令 UI 化、哪些留命令"的一次分类实践。

**坑①：`stop()` 里 `taskkill` 静默失败，还谎报"已停止"**

- 现象：`autostart stop` 打印"已结束 PID 5028"，结果 `netstat` 一看 8787 还被 5028 占着，新进程起来就端口占用退出。

- 教训：**杀进程 / 删文件这类"有失败可能、失败后果严重"的动作，做完必须校验**，不能 fire-and-forget。

**坑②：切换朋友后，两条时间线串台**

- 现象：网页端切到另一个朋友，聊天区还是旧朋友的消息，新朋友的消息接着往下排——全乱套。
- 原因：消息靠 `after=lastId` 增量拉，切库后 `lastId` 还是旧库的最大 id。
- 修：切换（`/friend` / `/new-friend`）后前端**清空聊天区 + `lastId=0`**，重新从新库拉。
- 教训：**任何"换数据源"的操作，都要想清楚客户端侧的状态（分页游标/缓存）要不要重置**。这条在网页端特别容易漏。

**坑③：受限会话 kill 不掉外部进程（PID 空间隔离）**

- 现象：沙箱里 `taskkill` 报 "process not found"、Python `OpenProcess` 也拿不到，但系统 `Get-Process` 明明能看到 5028。等于"我启动的服务，我在沙箱里关不掉它"。
- 判断：受限会话有独立的进程视图/PID 空间，看不到宿主里其他进程。
- 处置：不硬刚——代码改正确（校验杀没杀掉），把"手动重启一次"交给用户；以后改后端代码用网页上的 `/restart`（进程自己退出，不依赖外部 kill），绕开这个限制。
- 教训：**自动化环境里"杀进程"不可靠时，优先让目标进程自己退出**（优雅退出信号 / 自毁命令），而不是从外面 kill。

**设计取舍①：命令输出放哪——面板，不是聊天流**

按钮触发的命令（`/memories`、`/diary` 这种一屏多行的）如果塞进聊天区，会把对话冲得七零八落。改成侧栏一个**输出面板**（pre 滚动区）：按钮触发 → 进面板；输入框里手敲的命令 → 照旧进聊天区（用户主动要的，他预期在那里看到）。两条路分开，互不污染。

**设计取舍②：为什么要 `/restart` 而不是"网页里直接 `/guard` 那样热重载"**

改了 `webui.py` 这类**已在内存里实例化的模块**（handler 闭包、已 bind 的 socket），`/refresh` 那套 `importlib.reload` 救不回来——得进程真重启。加 `/restart`：网页点一下 → 服务进程自己 `os._exit(0)` → 守护 5 秒后拉新进程。**前提是守护在跑**，否则提示"重启就再也起不来了"。这条和"stop 只在终端做"是同一个逻辑：别让网页能把服务玩死。

**未验证**：`/restart` 的实际重启链路、新朋友的盲盒流程、改名——都留用户手动点一遍。

### 实测反馈记录 #21（2026-10-09，Web 反馈一轮）

**背景**：网页端跑起来后，用户集中报了两条 bug + 四条建议。两条 bug 分别踩了"时间戳只有 HH:MM 分不清新旧"和"AI 从上下文脑补、静默覆盖稳定字段"两个坑；四条建议里，profile/记忆**留痕**是架构性要求。

**坑①：消息时间戳只显示 HH:MM，跨天分不清**

- 现象：所有消息只显示 `HH:MM`，昨天和今天的消息看不出区别。
- 修：今天只显 `HH:MM`；昨天显"昨天 HH:MM"；更早显 `MM-DD HH:MM`（跨年带年份）；且换天插一条居中**日期分隔条**（微信/Telegram 风格）。前端 `lastMsgDay` 记住上一条的日期，换天才插分隔条；切朋友清空聊天区时一并重置。

**坑②：AI 从上下文脑补，静默覆盖了稳定 profile 字段（本轮核心）**

- 现象：用户"一直是夜猫子"，但小葵的清单里写着"作息习惯：基本十一点多就困，偶尔刷手机拖到十二点"。用户从没说过 12 点睡。
- 根因：提取器看到某段上下文（可能是"我要睡了/晚安"之类）就脑补出"作息习惯"并**静默覆盖**——原 `_apply_profile` 里"AI 自己写过的字段就更新值"，没有任何冲突判断，也没留证据。
- 修（三层）：
  1. **留痕**：每次自动填 profile 字段，把"上下文证据"（当时对话原文）存 **B 库**（`long_memories`），**A 库那条记忆挂 `long_id` 指向证据**；`/profile` 显示 `〔证据#N〕`、`/profile why <字段>` 看原文。
  2. **稳定字段不静默覆盖**：作息/生日/城市/称呼等**身份级字段**遇到与旧值冲突的新说法，**标 `pending` 待用户确认**，不直接改（`/profile pending/accept/reject`）；可变字段（在忙的事等）照旧可更新。
  3. **有疑惑主动交流**：有 pending 时往 system prompt 注入提示，让 AI 下一条消息自然地跟用户核实"我记得你是夜猫子，怎么这次感觉睡得早了？"，而不是自己悄悄改。
- 教训：**"AI 自己写过的字段可更新"这个规则本身就是 bug 源头**——稳定字段和可变字段要分开，稳定字段的改动必须走"冲突→确认"；且任何自动写入都要留证据，否则用户没法判断 AI 是不是脑补。

**设计取舍①：证据走 A/B 库，不另起一套存储**

profile 字段的证据复用现成的 `long_memories`（B 库），A 库记忆的 `long_id` 直接指向证据——语义上就是"A 库摘要挂链接 → B 库全文"，和长文本是同一套，不额外加表。

**设计取舍②：稳定字段 / 可变字段怎么分**

`STABLE_PROFILE_FIELDS = {称呼/生日/城市/所在城市/作息习惯/职业/专业/职业-专业/学校/年级}`；其余（在忙的事/兴趣爱好/喜欢的内容类型/雷区/其他）算可变。判据：身份级、错了很伤人、极少变的 → 稳定；自然流动、常更新的 → 可变。

### 实测反馈记录 #22（2026-10-09，命令输出糊成一坨）

**现象**：在输入框里敲 `/help`（或 `/status`、`/memories` 等任何多行命令），输出在聊天区挤成一坨、换行全没了；但点侧栏按钮触发的同名命令，输出正常分行。

**根因**：两条渲染路径不一致。按钮触发 → `runCmd()` → `panelDone()` → 写进 `<pre id="pOut">`，`<pre>` 默认保留换行；输入框手敲 → `send()` → `addSys()` → 生成 `.msg.sys` 元素，而 `.msg.sys` 的 CSS 既没有 `white-space:pre-wrap`（浏览器把多行文本的 `\n` 折叠成空格），又是 `text-align:center`（HELP 里用来对齐的空格也失效）。

**修**：给 `.msg.sys` 补 `white-space:pre-wrap` + `text-align:left` + 等宽字体（`ui-monospace,Consolas,monospace`），并 `align-self` 由 center 改 flex-start，命令输出块靠左、保留换行与空格对齐。

**教训**：同一个数据（命令输出）走了两条渲染路径时，要保证两边的换行/对齐策略一致；给任何"会放多行文本"的容器默认想清楚 white-space。

### 实测反馈记录 #23（2026-10-09，打断成本机制落地）

**背景**：S3 招牌「打断成本机制 + HUD」落地。需求文档只给了公式 `costIndex = R×(1+F)` 和三态 welcomed/tolerated/costly，但 R、F 的具体语义和阈值没展开——落地时需要拍三个设计决策。

**设计①：F 定为"疲劳"（精力推），不是"熟悉度"**

- 需求文档只说"R 由 phase/flow 给"，F 没指定来源。候选有"熟悉度（关系阶段）"和"疲劳（精力）"。
- 选疲劳的理由：①工作系统的 energy 是现成数据源；②HUD 已常驻展示精力，打断成本能直接联动；③"熟悉度"方向存疑——越熟的朋友被打断应该越欢迎，但 `(1+F)` 里 F 越大 costIndex 越大、反而更 costly，语义打架。
- 公式：F = (ENERGY_MAX − energy) / ENERGY_MAX，精力越低越累、打断代价越高。

**设计②：三态阈值 0.4 / 0.9（可配）**

- R 系数：心流 1.0 > 忙 0.7 > 闲（idle/break）0.3 > 收工 0；F∈[0,1]，故 costIndex∈[0,2]。
- 阈值卡 0.4（welcomed/tolerated）和 0.9（tolerated/costly），保证：心流期恒 costly（1.0 起）、收工恒 welcomed（0）、闲偏 welcomed、忙随精力在 tolerated↔costly 间浮动。
- 全参数化进 config（`COST_R_*`、`COST_WELCOMED_MAX`、`COST_TOLERATED_MAX`），`.env` 可调、`/refresh` 生效。

**设计③：红线兜底 = 换安全句，不是正则改写**

- 需求文档要求"命中归因措辞兜底改写"。正则改写（把"你打断我"换成"我刚忙"）不可靠、易出新错。
- 选确定性替换：命中 `COST_BLAME` 时整条回复换成 `corpus.COST_SAFE_LINES` 里一句"只说自己的状态"的话。宁可丢一条内容，也不发归因措辞。prompt 已强约束，命中很罕见，替换成本可忽略。

**设计④：紧急窗口内跳过打断成本**

- 急事当前是安全阀，打断成本应归零。`context` 里紧急窗口注入「急事」提示、跳过「此刻的相处」语态，避免两条指令打架（一条说"先听TA说"、一条说"你正忙回复短一点"）。

### 实测反馈记录 #26（2026-10-10，服务器实测四 bug：起床双语义 / 工作意识 / 主动瞎编 / 发送双发）

**背景**：用户把部署转到自己的服务器（https://derp.charlie2kabu.xyz:8443/），个人体验从本地迁到服务器；数据库以服务器聊天记录为准。服务器实测抓出四个 bug（前三个是新报，第四个是 #25 的落地修复）。

**Bug①：起床双语义混用 → 永远赖床、一整天不醒（最重）**

- 服务器实锤：12:38 state 还是 SLEEPY，`rest_schedule` 里 `wake_day=10-10` 但 `wake_at` 指向 **10-11**（明天）。
- 根因链：起床时刻有两个语义——`wake_up` 锚点 cron（早晨）问的是"**今天**该几点起"（赖床浮动后可能还没到）；夜里 SLEEPING 的 tick 问的是"**下次**几点起"（今天的已过 → 明天）。老实现只有一个 `next_wake_at`，`wake_base <= now 就 +1 天`——早晨 cron 一触发（锚点 8:30 ≤ now）就把"今天的起床点"翻成明天 → 进 SLEEPY(lie_in) 等一个永远等不到的时刻 → 一整天不醒。

**Bug②：有工作系统没有工作意识（进度条涨了、人说在睡觉）**

- 用户反馈："明明进度条显示完成了一部分任务，还说自己在睡觉"。

- 修复（用户拍板"少做几件"）：**醒来才排班**——`work._state` 只在"过了实际起床点且不在 SLEEPING"时排班；没醒 plan 空、HUD 进度不涨；赖床晚起 → 排班起点移到实际起床点之后，可用时间变短自然**少排几件**。

**Bug③：主动消息瞎编开场 + 把别人的记忆安到用户头上**

- 现象：小葵主动消息倒数第二句问候是编的（"好久没聊"——其实 2 小时前刚聊过），最后一句摸不着头脑（翻出一条小葵**自己**的旧记忆硬套"想起关于TA的事"模板）。

**Bug④：网页端发送文字出现两次（#25 落地）**

- 根因确认：`send()` 手动回显后 `lastId` 没推进，轮询又把同一条拉出来渲染一遍。

### 实测反馈记录 #27（2026-10-10，修 #26 过程中测试抓到的三个连带坑）

**坑①：起床缓存单槽被"今天/明天"翻转 → 夜里每分钟一个新起床点**

- `next_wake_at` 夜里要查"明天的起床点"，但缓存只有一个槽（wake_day/wake_at）：查明天会把缓存翻到明天、下一次查今天又翻回来——每次翻转都随机重算。夜里 tick 每分钟调一次 `next_wake_at`，起床点每分钟都在抖。
- 修复：缓存改 `wake_days` **按日 dict**，今天和明天并存互不干扰；旧的 wake_day/wake_at 字段继续维护（向后兼容）。

**坑②：SLEEPING 睡过头兜底失效 → 错过 cron 会睡一整天**

- SLEEPING 的 tick 兜底原来用 `next_wake_at`，但早晨生活日翻篇后"下次"就指向**明天**——电脑睡到中午开机，兜底判定"还没到下次起床"，继续睡到第二天。
- 修复：兜底改 `_in_morning(now) and now >= today_wake_at(now)`（今天的起床点过了就醒）。

**坑③：凌晨误唤醒**

### 实测反馈记录 #31（2026-10-10，Web 两 bug：发送排队到回复完才发出去 / 偶发重复消息）

**现象**：①网页端连发多条消息，全部卡在队列里，TA 回复完才一起发出去；②偶发同一条用户消息出现两次。

### 实测反馈记录 #32（2026-10-10，今日上下文 + 艾宾浩斯记忆衰减，v0.51）

**背景**：用户提议「一天所有信息交流都进记忆，阅读内容存 B 库并注入上下文，写日记后从上下文清除但记忆保留；再加艾宾浩斯遗忘——遗忘=一次次总结，总结够次数彻底遗忘，重复调用延长保持时间，够多次永久记住」。

**落地**：①工作产出素材时顺手落 B 库（`tags=今日素材`，**不额外调 LLM**——素材文本已经生成好了），`context` 每轮注入「你今天做过的事」，筛选条件是"创建于今天" → **跨天自动不再注入**（就是用户要的"写日记后从上下文清除"），B 库记录保留。②`memories` 加 `decay_level`/`pinned` 两列（旧库自动迁移）：距最后一次被想起超过「`IDLE_DAYS ×(1+召回次数×BONUS)`」天 → 压短一级，压到 `MAX_LEVEL` 删行（连带删挂的 B 库长文 + 向量）；`recall_count ≥ PIN_RECALLS` → 永久。

**几个设计取舍**：

- **遗忘挂在睡前复盘里，不另起进程**：一天一次、一次批量 LLM 调用压缩全部待衰减项；LLM 不可用就跳过下次再试（绝不拿空结果误删）。
- **保真优先于衰减**：压缩结果比原文长 / 踩 `_validate` 红线 / 短于 6 字 → 本次跳过不改。总结链漂移是真风险（压三次可能"养猫叫团子"变成"喜欢小动物"），所以宁可不淡忘也不让记忆变味。
- **B 库长文不单独分级衰减**：它是原文证据（书摘/长对话），只在挂着的 A 库记忆被删除时一起删。
- **不做「全量对话常驻上下文」**：`messages` 表本来就是全量记录，真需要靠 `recall` 拿；常驻会让每条消息 token 翻几倍还稀释记忆/人设的权重。
- **命令命名**：`/forget <编号>` 早已被"删事实便签"占用，遗忘命令改叫 `/decay`（`/decay dry` 只预览）。

### 实测反馈记录 #33（2026-10-10，换朋友永远卡在"稍等一下"——SEND_LOCK 重入自锁死）

**现象**：网页端点「换朋友」（星仔 → 小葵）面板一直显示"稍等一下"，再也回不来。

**根因**：v0.51 修 #30 时引入。`/api/send` 外层 `with db.SEND_LOCK:` 包住 `on_message()`，而切库命令 `/friend`、`/new-friend` 内部为了保证「切库期间消息不进错库」又要 `with db.PATH_LOCK, db.SEND_LOCK:` ——**同一个线程对同一把锁重入**，而 `SEND_LOCK` 当时是普通 `threading.Lock`（不可重入）→ 自锁死。`/api/send` 那个请求线程永久阻塞，浏览器收不到响应。

**修复**：`SEND_LOCK` 改 `threading.RLock()`（`PATH_LOCK` 本来就必须是 RLock，同一个道理）。加了回归测试：子线程跑完整调用链（外握 SEND_LOCK → `/friend 1`），8 秒超时断言线程还活着且返回"欢迎回来"。

**教训**：给已有锁**新增获取点**时（尤其是"命令内部 + 调用方外层"都会拿），第一件事是确认它可重入；不可重入锁只要有一处嵌套获取就是死。另：切库仍要等 `PATH_LOCK`（回复生成全程握着它，含打字 sleep），所以**TA 正在回复时切换最多等几十秒**是既有行为，不是卡死——真卡死是永久不返回。
