# 方案审查基准（REVIEW-CRITERIA）

> **📋 本文档职责**：worker3（方案审查者）审查 `docs/PLAN-*.md`（worker1 产出）时使用的**项目内具体判据**——四维度（合理性 / 复杂度 / 遗漏 / 框架契合）各自在本项目里"什么算不过关"，具体到文件与模块，不泛泛而谈。
> **🚫 本文档不管**：项目需求与状态（→ [需求概要-朋友型AI.md](./需求概要-朋友型AI.md)）、工作流（→ [AGENTS.md](../AGENTS.md)）、文件同步对照（→ [文件改动同步清单.md](./文件改动同步清单.md)）。
> **📌 审查产出**：方案出现后写 `docs/REVIEW-<YYYYMMDD>-plan.md`（结构见文末）。
> 基准基线：**v0.109（main@45cff31，2026-10-18 核对与远端同步）**。引用行号以此为准；方案里引用的行号/模块若与最新 main 不符，先怀疑方案基于过期基线。

## 维度一：方案是否合理（目标 / 验收 / 因果）

### 1.1 验收标准必须可执行，且套进本项目「完成」的定义

本项目的完成 ≠ 代码写完。AGENTS.md「改完必做」定义了五步链：**代码（含调试面板入口）→ 全量测试（`EXPECTED_TOTAL` 同步）→ 文档三处（需求概要版本记录 + 需求池状态 + 实测索引）→ commit → `sync-to-server.sh`**。方案若只描述代码步骤、不写验收链，视为目标不完整：

- [ ] 方案是否写明**目标版本号**，且该版本号未被占用（先 `git fetch origin main` 核对——v0.90 版本号撞车是实录教训，见 AGENTS.md 步骤 0）。
- [ ] 是否写明**测试影响**：新增几个用例、进哪个 `test_*.py`、`run_tests.py` 的 `EXPECTED_TOTAL`（现为 92）要不要加。只说"会加测试"不算数。
- [ ] 是否写明**文档同步点**：需求池哪个条目要改状态、`docs/文件改动同步清单.md` 要不要补行、要不要写实测反馈。
- [ ] 是否写明**调试面板入口**（v0.105 起项目约定：新增可调试功能——命令/增删改数据/开关——都要进网页调试面板 `#foldDebug`，后端接口在 `webui.py` 的 `do_GET`/`do_POST`）。
- [ ] 每个步骤能否回答"**失败了怎么知道**"：有没有可观察的失败信号（测试红 / 自检输出 / 行为变化），还是只能靠"感觉对了"。

### 1.2 因果漏洞的高发区（本项目特有）

- **"删 X 就能好 Y"类断言**：本项目删过 random_chat/nudge/noon（v0.103）、判官、游戏模式注入（v0.104），每次都先确认了**唯一消费者**才删。方案要删除任何东西，必须列出它的全部调用方并逐一交代去向（`grep` 可验证）。
- **"加个参数就能调好"类断言**：可调参数 = `config.py` + `.env.example` + `tuning.py`（元数据清单，88 参数/9 组）三处同步，且 tuning 断言 `test_tuning_panel` 校验组数。方案低估这个成本的，算因果漏洞。
- **"prompt 里说一句就行"类断言**：本项目 prompt 约束有配套的**确定性代码兜底**传统（提取器 `_validate`、红线 `redline_report()` 只告警、词表进 `corpus`）。纯 prompt 方案要问：LLM 不听话时谁兜底。
- **时间/作息相关断言**：本项目"现在几点"渗透一切（生活日、phase、排班、日历触点）。方案声称某行为"到点发生"，要能指出由哪个 tick/cron 驱动（`scheduler.py` 的 cron、`life.tick()`、`events.calendar_tick`、`core.check_share_impulse`——这四个是现存驱动源）。

## 维度二：是否复杂化了问题

### 2.1 硬信号（见到即可质疑）

| 信号 | 本项目判据 |
| --- | --- |
| **引入新 pip 依赖** | `requirements.txt` 现仅 4 个直接依赖，`sources.py` 用标准库 XML 解析实现 RSS/Atom 是刻意先例（零新依赖）。新依赖 = 本地 + 服务器双端安装 + `sync-to-server.sh` 链路验证，必须有"标准库确实做不到"的证据。 |
| **改数据结构（体验期）** | `体验优化清单.md` 尾部「体验期口径」明文：**小步、可回滚、不改数据结构**。体验期方案动 schema（加表/加列/改 kv 结构）直接触发"该进正式方案还是砍掉"的追问。 |
| **新增 LLM 调用点** | 项目对每轮 LLM 次数敏感：判官因"每轮一次白调用"被退役（v0.103）、独白层限 `max_tokens=400`、章节结算有串行闸门 `_settling`。方案加 LLM 调用必须写清**频次**（每轮/每天/每章？）与失败路径。 |
| **新抽象层 / 新模块** | 先问三个问题：①现有 `tools.py` 注册表 / `context.py` 组装 / `corpus.py` 词表 / `tuning.py` 参数能不能承载？②影响是否 ≥3 个模块（不到了就别建 `方案-*.md` 级别的东西，同步清单 docs 行的建档门槛）？③删起来容易吗（体验期口径：可回滚）？ |
| **跨模块重构** | `life.py` 的 phase 键集合（idle/working/flow/break/off/sleep）是**跨模块契约**，消费方十个模块（cost/mood/tone/offline/persona/webui/stream/commands/context/scheduler）。动它 = 十处核对，方案没逐个列消费方就不算想过。 |
| **"顺手"重构** | 体验期口径明文："顺手重构"进正式方案、不混进体验批次。方案里出现与主线目标无关的重构段，要求砍出去。 |

### 2.2 更小改动的检查清单（每条意见尽量给出）

按从轻到重的顺序问：

1. **现有参数能不能调出来**：`tuning.py` 88 个参数 + `config.py` 环境变量（`/refresh` 热生效）——很多"行为不对"是参数问题不是代码问题。
2. **现有词表/语料能不能加**：`corpus.py` 的匹配词表（兴趣信号/紧急信号/追问词）都是加一行就能扩的。
3. **现有注入块能不能改**：`context.py` 的动态区注入、【我今天刷到的】这类块，改措辞比加机制便宜。
4. **现有工具能不能挂**：新 function calling 能力优先注册进 `tools.py`（`register(Spec)`），别另起调用机制。
5. **写死行不行**：`life.py:37-42` 有先例——推导口径的组成部分（`NOMINAL_SESSION_MIN` 等）**刻意不进 config**，注释明写"不是可调旋钮"。能写死的别做成可调。

### 2.3 收益/成本过关吗（本项目的砍单传统）

需求概要第四节有完整砍单史：对话双线（每轮两次 LLM 换"回复不突兀"，收益不确定 → 砍）、时间计划系统（自用用不上 → 砍）、每晚可靠窗口（"没在工作自然就可以找到" → 砍）。方案要能回答：**这个收益值这个成本吗**——尤其项目是单人自用（单用户、单机、无并发用户），为假想的规模/多用户做的设计直接质疑。

## 维度三：是否有未考虑的地方（风险覆盖清单）

方案触及以下任何区域而没有交代对应风险，即算遗漏：

### 3.1 并发与锁（本项目事故高发区）

- **两把锁**：`db.py:13 PATH_LOCK`（全流程互斥）/ `db.py:22 SEND_LOCK`（收发与切库互斥），都是 RLock。锁序规则：切库命令 = **PATH_LOCK 内套 SEND_LOCK，别反**（`webui.py` 行，实测 #31/#33 的教训）。
- **后台线程跨切库写**：v0.109 刚修的 `_settle_one` 章节结算线程——先读计划、再调 LLM、最后落库，中途主线程切库就把旧库数据写进新库。**方案引入任何新后台线程，必须有同款保护**（记下发起时 `config.DB_PATH`，进 `db.PATH_LOCK` 后复核，变了就放弃）。互斥闸门先例：`life.py` 的 `_settling` / `_browsing`。
- **多朋友切库**：每朋友一份 `friend-<id>.db`，任何"当前库"假设都要过切库场景。

### 3.2 数据迁移与向后兼容

- **加表/加列必须带旧库迁移**（`db.py` `_SCHEMA` + `info_items.noted` 列是先例）。存量库在服务器上，迁移没写 = 线上第一启动就崩。
- **配置键兼容**：先例 `LLM_REASONING_EFFORT` 读兼容旧 `DEEPSEEK_EFFORT`（v0.102）。改名/换键要有读兼容或一次性迁移说明。
- **删除公开接口**：先例 `MEMORY_TOOLS`/`run_memory_tool` 在 `memory.py` 留向后兼容别名；`test_p1_features.py` 保留转发 shim。删接口 = 列出所有引用点一次改完，或留别名。
- **服务器是数据唯一真相**：本地 `friend.db` 只作调试，方案里有任何"改库"步骤必须区分本地/服务器，且**绝不能设计成从本地覆盖服务器**。

### 3.3 测试覆盖（本项目有硬闸门）

- 新用例写进对应 `test_*.py` 即自动收集；**`EXPECTED_TOTAL`（`run_tests.py:33`，现 92）必须同步**，不同步 = 闸门直接报错，改动算没做完。
- **改完跑全量**，不是只跑新增域（`python run_tests.py`）。
- 测试纪律（`_test_common.py`，约定 #10/#11）：DB 重定向/config 改值一律 `_patch_config`；真实收发流程套 `_FAST_TIMING`；手造 `day_state` 必须 `v:2 + planned:1`；与"现在几点"解耦（`WORK_ENABLED=False` / 预置 `rest_schedule`）；临时产物只进 `.test-tmp/`；`WORK_SHAREABLE_ENABLED` 全局 off、需要结算的用例局部打开（v0.109）。方案声称的测试步骤若出现手写 save/restore、裸 `tempfile.mkdtemp()`、精力字段直接造假，即违反纪律。
- **偶发测试**：涉及后台线程的改动，验收标准里"连跑 N 次全量"比"跑一次绿"有说服力（v0.109 用 30/30 验证偶发根因修复）。

### 3.4 性能与高频路径

- **缓存稳定前缀**：`context.py` 的动态注入必须放动态区、别破坏前缀（`context.py:80-85` 约定）。方案往 system prompt 塞东西要指明位置。
- **`life.status()` / `hud()` 是高频读**：被 HUD/意识流/成本/每轮聊天路径反复调——判定逻辑（有副作用的）不能放进去，`browse` 挂点只放 `tick()` 是 v0.97 的明确教训。
- **prompt 长度**：注入块越多每轮 token 越贵，方案加注入块要有"空则整块不出现"的同款守护（【我今天刷到的】先例）。

### 3.5 被忽略的调用方（易漏清单）

- `core.on_user_message` **必须返回消息落库 id**（网页端轮询游标，实测 #25）；`/api/send` 返回消息 id；`/api/state` 的 `materials` 是**顶层字段**。
- `channels/base.py` 基类方法签名改动 = 四个通道实现同步改。
- `persona_pool` 加骨架要同步四处（`KERNEL_*` / `KERNELS` / `POOL` / `_LABEL_TO_KEY` 反推表）。
- `webui.py` 与 CLI 共用同一份 db——任何新存储都是绕开既有机制。
- 前端接线断言加进既有「网页端 Web UI」用例内部，不单开用例（v0.101 先例，`EXPECTED_TOTAL` 不变）。

### 3.6 失败路径与降级

- LLM 失败**不落库污染上下文**（`core._is_llm_error`，v0.88 C2）。
- 增强类能力必须可降级：`embeddings.py` 缺模型退回纯字面、`sources.py` 超时/坏 XML 返回空不崩、"是增强不是必须"。
- 网络/外部服务：SSRF 守卫在位（`urlparse().hostname` 而非 `netloc`、`172.16–172.31` 区间判定、重定向逐跳验）——方案加任何外部取数要过这道。

## 维度四：是否偏离或浪费了现有框架

### 4.1 不该被绕过的既有机制（绕过 = 除非方案给出明确理由）

| 机制 | 位置 | 绕过的表现 |
| --- | --- | --- |
| 工具注册表 | `tools.py`（`register(Spec)` + gate + 预算原语） | 在 `core` 里写 if 链工具循环；新工具不挂 gate |
| 统一上下文组装 | `context.py`（便签>profile>记忆>上下文；三个 build 入口） | 在 core/webui 里自己拼 system prompt |
| 固定语料库 | `corpus.py`（会扩充的固定文案 + 匹配词表） | 业务模块里硬编码文案/词表 |
| 锁与库管理 | `db.py`（PATH_LOCK/SEND_LOCK/`_SCHEMA`） | 自己加锁、绕开锁序、直连 sqlite 文件 |
| 测试公共机制 | `_test_common.py` | 手写 config 还原样板、临时目录不收口 |
| 参数双头维护 | `config.py` + `tuning.py` + `.env.example` | 只改一处；tuning 默认值手写不走 `getattr(config,k)` |
| 凭据唯一真相 | `.env`（`auth.write_env` + 热生效） | 另起存储存配置/凭据 |
| 调试面板 | `web/index.html` `#foldDebug` + `webui.py` | 新增可调试功能只留 CLI 斜杠命令 |
| 内部 LLM 人设 | `persona.core_identity_prompt()` | 后台调用拼 `build_system_prompt()`（递归爆栈，实测 #17） |

### 4.2 别复活已退役的东西（复活 = 需要说明为什么当初退役的理由已不成立）

- `work.py` / `reading.py`（v0.90 被 `life.py` 取代，已删除）。
- 群聊全套（v0.27 砍，`test_no_groupchat_leftovers` 兜底）。
- random_chat / nudge / noon 三个无理由定时通道 + 判官 `_judge_session_end` + `session_open`（v0.103 退役——"话语权来自念头，不来自定时器与骰子"是拍板过的方向）。
- 游戏作为「模式」（v0.104 起规则活在 `GAMES[k]["recall"]` 意识流里，`prompt_injection()` 已删）。
- `schtasks.exe`（用 `autostart._ps()`）、`os.kill(pid, 0)`（用 `autostart._pid_alive()`）。

### 4.3 硬性约定（AGENTS.md 十二条，方案文本本身也可能踩）

审查方案文档时同步检查：一视同仁（不出现"为了你/用户特殊化"主语）、工具拟人化两层分离（契约词不许改）、代价只呈现不归因、称呼不写死、语料只装会扩充的两类、需求池打勾纪律（"预留/待做"不许整条 ✅）。

### 4.4 已知的命名张力（固定意见，不重复展开）

worker1 的方案落在 `docs/PLAN-*.md`，而项目既有方案文档约定是 `方案-<主题>-v<版本>.md`（同步清单 docs 行）。**这不阻塞审查**（协作协议由编排者定），但方案若要落地为正式文档，应迁移进 `方案-*.md` 体系并在需求池挂链接——每份 REVIEW 里保留这一条提醒。

## 判定等级

| 等级 | 判据 |
| --- | --- |
| **通过** | 四维度无硬伤；剩余意见是改进建议，不阻塞开工 |
| **有条件通过** | 主体合理，但存在：证据不足的断言（须补）/ 该砍的 scope（须砍）/ 未覆盖的必须风险（须补）。条件清单逐条列出，全部满足才可开工 |
| **打回** | 触发任一：踩 4.1/4.2 硬红线且无理由说明；2.1 硬信号成立且无更小替代；验收链缺失（1.1 全空）；基于过期基线（引用的版本/模块/行号与最新 main 不符且影响结论）；版本号撞车 |

## 审查产出格式（`docs/REVIEW-<YYYYMMDD>-plan.md`）

1. **结论先行**：通过 / 有条件通过 / 打回 + 一句话理由。
2. **逐条意见**：`位置（方案章节/行号）→ 问题 → 证据（文件:行号 / 命令输出，不确定的标「未验证」）→ 建议`。
3. **清单汇总**：证据不足的断言（要求补证据）/ scope 该砍的部分 / 遗漏的风险。
4. **更简单的替代做法**：至少 1 条，并说明为什么更简单（对照 2.2 检查清单的层级）。
5. 固定提醒：4.4 命名张力（一句话）。
