## 3. 新任务模型（核心：彻底重写 `work.py` 状态机）

### 3.1 一句话模型

> 一天 = 从「实际醒来」起排的一段**任务时段**（8 半节 + 休息模板，内容=读书）；**进度 = 有效阅读时长 ÷ 应读时长**（字数只是叙事换算）；**经验 = 进度百分比**；半节是休息节奏，章节边界是笔记结算点，起晚自然少读、不追进度。

### 3.2 时间轴：任务时段模板（锚定实际起床，r2 补齐项 A/C）

- **锚点** = `_wake_point(now)`（作息系统的实际起床点，`work.py:80-88` 已有，保留）+ 磨蹭 `WORK_WARMUP_MIN`（默认 50，带 `_jitter` 同款抖动；现在是硬编码 `randint(15,90)`，`work.py:100` → 提参数）。
- 模板：上午 `SCHED_MORNING_PERIODS` 节（每节 = 上半 40 + 节内休 15 + 下半 40，节间休 20）→ 午休 `SCHED_LUNCH_MIN`（新，默认 120）→ 下午 `SCHED_AFTERNOON_PERIODS` 节。`half_periods()` 增加 `start` 参数从锚点起排，**去掉对 `SCHED_WORK_START/LUNCH_START/LUNCH_END/WORK_END` 的依赖**。
- **下班点** = 最后一个半节的结束时刻（由锚点推出，不再读 17:30）。加班从下班点到「读完或睡前」。
- 排班仍是「醒来才排、同一天幂等」（`_state` 的 planned 机制保留）。

### 3.3 进度与经验（拍板 #3/#4/#7 的落地；r2 关闭原待确认点 #1）

- 当日计划：`trueread.plan_day` 圈定整数章节 → `total_chars`（已有，保留）。
- 应读时长 `T` = 8 半节 × `SCHED_HALF_PERIOD_MIN` = 320min（`total_teaching_min()` 已有）。**tps = total_chars ÷ T**（已有，保留——推导值不单独设）。
- **有效阅读分钟 M(now)** = 「锚点 → now」与今日任务窗口（半节窗口 ∪ 加班窗口）的交集总长。**已读字数 = M × tps；进度 = 已读字数 ÷ total_chars = M ÷ T**。
- 推论（这就是拍板 #7 和「分钟 × tps」的合一之处）：**进度本质 = 有效阅读时长占比**。起晚 → 锚点后移 → 上午半节被吃掉 → M 少 → 进度低，**天然不追进度，不需要任何特判**。原 r1 待确认点 #1 就此关闭。
- **经验 = round(进度 × 100)**，即时呈现；当日进度 100% 才是满经验 100。收工时意识流记一笔「今天攒了 X 点经验」。跨日累计仍待拍板（§12）。
- 简化决策（明说，防以后疑惑）：M 按墙钟累计，**聊天打断的分钟不扣除**——打断的代价由打断成本（cost）与精力叙事承担，读书进度只是被推后（窗口照走，与旧单元制行为一致）。要细扣「被打断分钟」是后续增强，不在本次。

### 3.4 章节结算（触发 / 互斥 / 冷启动 / 回写 progress）

- **触发**：已读字数跨过圈定章节的累计字数边界（纯派生判定，零 LLM）。边界 = `cumsum(chapter.char_count)`。
- **结算动作**（后台线程，LLM）：沿用 `trueread.settle_chapter`（思考 buffer + 章节节选 → 短概述/完整转述/打动）→ 读书笔记 alpha/beta + 向量索引 + 打动进素材池/待办。触发文案改「读到第 N 章末」。
- **互斥与冷启动**（吸收 v0.88 R2）：结算入口唯一化——`status()/tick()` 惰性推边界，跨过即入**串行后台队列**（同时只跑 1 个，复用 `_generating` 同款闸门）；队列深度 ≤3，更早跨过的章**只推指针 + 意识流记一笔，不补笔记**（防电脑睡一天回来冷启动补账触发 LLM 尖峰）。
- **幂等**：kv 存 `settled_idx`（已结算章数）作为唯一事实，结算成功才推进；游标（在读第几章）改为**派生值** = 第一个「累计边界 > 已读字数」的章。
- **回写 `library.progress`**（拍板 #11 后半）：每结算一章，回写 `book_id` + 该章末段落序号（口径与跳读回写一致，`library.py:720`）——治「第 801 段」卡住，`plan_day`/`_reading_line`/`prompt_hint` 从此读真进度。
- **泛化素材退役**（r2 补齐项 B）：`_SHARE_PROMPT`/`_produce_shareable`/`_gen_shareable` 的 article=None 路径整个删除。素材只来自章节结算的「打动」。无书可读 = 无素材 = random 主动消息自动跳过（与拍板 #8 闭环）。`interests.record` / `stream.append("read")` 随章节结算触发（修 v0.88 R5 的「成长闭环断了」）。

### 3.5 起晚与加班（拍板 #2/#5）

- **起晚**：排班时发现 `_wake_point` 晚于人格锚点（`_anchor`）→ `stream.once("late_wake")` 记「今天起晚了」（意识流一笔，让 TA 自己知道），之后一切照常——锚点后移自然压缩 M，速度不变、不追进度、经验打折。
- **加班**：过下班点进度 <100% → 加班窗口开启，M 继续按墙钟累计直到进度 100% 或**睡前**（`_bedtime` 已有；睡觉是硬边界，S3 已定）。加班期间 phase 仍为 `working`（不新增 phase 键），prompt_hint 加一句「过点了，还在把今天没读完的读完」。
- 进度 100% 或到睡前 → 收工（`off`，意识流记「今天的事忙完了」）。

### 3.6 精力（拍板 #6 的另一半）

保留 `WORK_ENERGY_MAX/COST/RECOVER`，语义从「每单元」改为「**每半节消耗、每次休（节内休/节间休/午休）恢复**」。惰性结算：按「已结束的半节数/已过的休息次数」补账（与旧 `_settle` 同款 while 循环，`work.py:155-201` 的骨架保留、内容重写）。

### 3.7 phase 契约不变（消费方零改动的保证）

**phase 键集合不变**：`idle / working / flow / break / off / sleep`。推导换源：

| phase | 新判定 |
| --- | --- |
| `flow` | 在半节内且进入该半节前 `WORK_FLOW_RATIO`（保留，作用于半节） |
| `working` | 半节其余时间 / 加班窗口 |
| `break` | 节内休 / 节间休 / 午休 |
| `idle` | 锚点前（磨蹭期）/ 排班后第一个半节前 |
| `off` | 进度 100% 收工 / 睡前收工 / 无书可读（`plan_day.done`） |
| `sleep` | 未醒 / `db.get_state()=="SLEEPING"`（不变） |

`cost/mood/offline/tone` 因此**零改动**（§2.2 已核实它们只读 phase/flow/energy）。

## 6. 主动消息收敛（拍板 #8，背景 #3）

- **`context._inject_random_topic` 改为返回 `bool`**（注没注进弹药）：素材（`work.take_shareable_item`）→ 兴趣（`interests.random_promoted`）→ 旧记忆（`memory.random_memory`）三源逐个试，注入成功返回 True。现有实现三源皆空时**静默落空**（`context.py:189-223` 尾部无 return ✓）→ LLM 自由发挥 → 「窗外车怠速」×4。
- **random 无弹药就不发**：`build_proactive_messages` 在 random 场景且三源皆空且无承诺（`selfmem.prompt_hint` 为空）时返回 None，`core` 主动循环拿到 None 直接跳过——**不调 LLM、不发消息**（承诺也算弹药，拍板 #8 列了它）。
- **`persona.PROACTIVE_SCENARIOS["random"]` 文案改**（`persona.py:321`）：删「刷手机看到的东西」（邀请编造），保留「正在读的书、聊到一半的事」；明确「没有真实想说的事就一条都不发」由代码兜底，不靠 prompt 自觉。
- 弹药查重（轻量，防换着花样重复同话题）：兴趣/记忆源**最近 48h 已注入过的跳过取下一条**；素材源已有 `used` 标记天然不重复。

## 8. 「10 点才醒」排查（拍板 #12，运维项——不阻塞动工，可与动工并行）

服务器常开却 10:06 才醒，按可能性排查（ssh `ubuntu@150.158.147.51`）：

1. **时区**：`timedatectl` + `systemctl show friend-ai -p Environment`——若系统 UTC，`datetime.now()` 全线偏 8 小时（但 10:06 北京 = 02:06 UTC，对不上纯时区，更像偏 2 小时或别的问题，以实测为准）；
2. **代码未同步**：服务器 `git -C /opt/friend-ai rev-parse HEAD` 对比本机——醒来判定逻辑在 `offline.today_wake_at`（历史 bug 区，`offline.py:20` 注释自述过「永远进 SLEEPY 赖床」一类坑）；
3. **赖床卡住**：`journalctl -u friend-ai --since 当天` 看状态机时间线（作息浮动的随机数是否把醒点推到很晚）；
4. 顺手：**本机→服务器 embedding 模型与 `.env` 的 `TZ` 是否设置**。
结论落 `docs/实测反馈/`，若真是代码 bug（如赖床浮动无上限），单独修，不混进本方案。
