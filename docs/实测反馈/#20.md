# 实测反馈记录 #20（2026-10-09，网页端操作 UI 化）

**背景**：网页端不能光靠输斜杠命令——换朋友、抽新朋友这种结构性操作在手机/网页上输 `/friend 3` 太反人类，得做成控件；但调试类（带参数、低频）保留输入框。这是"哪些命令 UI 化、哪些留命令"的一次分类实践。

**坑①：`stop()` 里 `taskkill` 静默失败，还谎报"已停止"**

- 现象：`autostart stop` 打印"已结束 PID 5028"，结果 `netstat` 一看 8787 还被 5028 占着，新进程起来就端口占用退出。
- 原因：`taskkill` 返回非零（权限不足），但代码没检查返回值，无条件当成成功。
- 修：杀完逐个 `_pid_alive()` 校验，还活着的如实报告"PID x 还活着（权限不足），请手动结束"，而不是报成功。
- 教训：**杀进程 / 删文件这类"有失败可能、失败后果严重"的动作，做完必须校验**，不能 fire-and-forget。

**坑②：切换朋友后，两条时间线串台**

- 现象：网页端切到另一个朋友，聊天区还是旧朋友的消息，新朋友的消息接着往下排——全乱套。
- 原因：消息靠 `after=lastId` 增量拉，切库后 `lastId` 还是旧库的最大 id。
- 修：切换（`/friend` / `/new-friend`）后前端**清空聊天区 + `lastId=0`**，重新从新库拉。
- 教训：**任何"换数据源"的操作，都要想清楚客户端侧的状态（分页游标/缓存）要不要重置**。这条在网页端特别容易漏。

**坑③：受限会话 kill 不掉外部进程（PID 空间隔离）**

- 现象：沙箱里 `taskkill` 报 "process not found"、Python `OpenProcess` 也拿不到，但系统 `Get-Process` 明明能看到 5028。等于"我启动的服务，我在沙箱里关不掉它"。
- 判断：受限会话有独立的进程视图/PID 空间，看不到宿主里其他进程。
- 处置：不硬刚——代码改正确（校验杀没杀掉），把"手动重启一次"交给用户；以后改后端代码用网页上的 `/restart`（进程自己退出，不依赖外部 kill），绕开这个限制。
- 教训：**自动化环境里"杀进程"不可靠时，优先让目标进程自己退出**（优雅退出信号 / 自毁命令），而不是从外面 kill。

**设计取舍①：命令输出放哪——面板，不是聊天流**

按钮触发的命令（`/memories`、`/diary` 这种一屏多行的）如果塞进聊天区，会把对话冲得七零八落。改成侧栏一个**输出面板**（pre 滚动区）：按钮触发 → 进面板；输入框里手敲的命令 → 照旧进聊天区（用户主动要的，他预期在那里看到）。两条路分开，互不污染。

**设计取舍②：为什么要 `/restart` 而不是"网页里直接 `/guard` 那样热重载"**

改了 `webui.py` 这类**已在内存里实例化的模块**（handler 闭包、已 bind 的 socket），`/refresh` 那套 `importlib.reload` 救不回来——得进程真重启。加 `/restart`：网页点一下 → 服务进程自己 `os._exit(0)` → 守护 5 秒后拉新进程。**前提是守护在跑**，否则提示"重启就再也起不来了"。这条和"stop 只在终端做"是同一个逻辑：别让网页能把服务玩死。

**未验证**：`/restart` 的实际重启链路、新朋友的盲盒流程、改名——都留用户手动点一遍。
