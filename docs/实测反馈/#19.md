# 实测反馈记录 #19（2026-10-09，网页端开机自启与常驻）

**背景**：自用阶段服务端跑本机，电脑一重启就得手动 `python main.py web`——那它不是"一直在那儿的朋友"，是"你想起来才去开一下的程序"。所以要两件事：**常驻**（崩了自己起来）+ **开机自启**（重启后自己回来）。

**坑①：`schtasks.exe` 在某些终端里根本不可用**

- 现象：`schtasks /create` 报 `ERROR: The system cannot find the path specified`；进一步测发现**连 `/query` 都是同样的错**，而同一台机器上任务计划服务（Schedule）明明是 Running。
- 判断：不是权限问题，是这个命令行工具在当前会话里不可用。
- 修：改走 Windows 的 `ScheduledTasks` 模块（`Register-ScheduledTask` / `Get-ScheduledTask` / `Unregister-ScheduledTask`），同一套东西、能拿到明确的报错文本。
- 教训：**命令行工具本身也可能是坑**，报错信息（"找不到路径"）会误导你去查路径，实际是工具不可用。写这类外部调用时，把失败原因（stderr）原样带回给用户，别只回一句"失败"。

**坑②：`os.kill(pid, 0)` 在 Windows 上不是探活，是杀人**

- 现象：写"进程还活着吗"时用了 POSIX 惯用法 `os.kill(pid, 0)` 期待"活着不抛错、死了抛 OSError"。
- 真相：CPython 在 Windows 上把 `os.kill` 实现成 **`TerminateProcess(handle, sig)`**——`sig=0` 也会被当成退出码传给 `TerminateProcess`。也就是说这行代码**会直接结束目标进程**。
- 修：改用 `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` + `GetExitCodeProcess`，退出码 `259`（STILL_ACTIVE）才算活着。
- 教训：**别把 POSIX 语义直接搬到 Windows**。这条如果漏了，后果是"查一下状态"把服务杀了，而且极难排查。

**坑③：vbs 中间层在受限环境跑不起来，改纯 Python 守护**

- 现象：原本设计是 `wscript.exe run_web_daemon.vbs` 当守护（vbs 里循环拉 `main.py web`）。实际跑下来 vbs 进程没起来、日志也没生成，等于整条链路静默失败——**没有任何报错**。
- 修：去掉 vbs 中间层，改成 `daemon.py`（纯 Python 守护）：用 `pythonw.exe` 跑它（无控制台窗口），它再用 `CREATE_NO_WINDOW` 拉起 `main.py web`，输出全部追写到 `logs/web.log`。整条链子无黑框、可观测。
- 教训：**跨语言的中间层（脚本调脚本调脚本）调试成本极高且失败是静默的**。能用同一种语言实现就别绕。

**设计取舍①：为什么必须有 `web.stop` 标志**

守护的目的是"崩了自拉"。但如果没有停止标志，你 kill 一次它起来一次，**永远关不掉**。所以 stop 分两步：写 `web.stop` 标志 + 杀进程；守护每次循环开头和进程退出后都检查标志，看到就退出。想恢复就 `autostart start`（自动清标志）。

**设计取舍②：为什么守护不放在网页进程里自检**

想过让 `webui.py` 自己带 watchdog 线程，但进程真崩了（或 OOM 被杀）内部线程也没了。必须是**外部独立进程**盯着。

**设计取舍③：为什么开机自启有两条路**

计划任务能查状态、能禁能删、不用管理员，是首选；但它依赖 COM，某些环境注册不了。所以兜底写「启动」文件夹（`%APPDATA%\Microsoft\Windows\Start Menu\Programs\Startup`）——零依赖、用户自己也能看懂和删掉。两条路都失败时，报错里把两条路的失败原因都列出来，并给手动兜底办法。

**未在本机验证的部分**：装/卸（`autostart on|off`）在受限会话里被拒绝（注册计划任务"拒绝访问"、写启动文件夹 PermissionError），需要用户在自己的普通终端里跑一次 `python main.py autostart on` 生效。测试只覆盖不碰系统的部分（路径一致、启动器内容、探活函数、status 不崩）。
