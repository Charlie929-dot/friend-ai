# #53 半夜不睡 + 无缘无故紧急模式 + 回复凭空消失（手机实测三条）

**日期**：2026-10-19 夜（用户手机实测） · **版本**：v0.111 修复

## 症状（用户报，三条）

1. 「今日凌晨，我上线小葵，不知为何超过睡觉时间很久都没有睡觉，而且还**无缘无故开了紧急模式**」。
2. 「手机端**输入框文字超过限制**会把输入框挤到左边，文字也会向右穿出输入框」。
3. 「聊天记录中的问题」——聊到一半，问了它没回。

## 诊断（服务器生产库 + 本地复现）

服务器 `/opt/friend-ai/friend.db`（与本机同为 CST），`consciousness_stream` / `messages` / `journalctl -u friend-ai` 三处对账。

### ① 整夜不睡：晚安后 40 秒自己把自己叫醒

`sleep → wake` 间隔 37–55 秒，**连着六晚全中**：

| 日期 | 入睡 | 起床 | 间隔 |
| --- | --- | --- | --- |
| 10-11 | 23:25:23 | 23:26:00 | 37s |
| 10-13 | 23:18:21 | 23:19:00 | 39s |
| 10-15 | 23:30:18 | 23:31:00 | 42s |
| 10-16 | 23:14:18 | 23:15:00 | 42s |
| 10-18 | 23:27:15 | 23:28:00 | 45s |
| 10-19 | 23:24:05 | 23:25:00 | 55s |

昨晚用户实际看到的：23:23:49「我先去睡了…晚安 🌙」→ 23:25:05「早！窗子那边光又斜进来一大片 ☀️」→ 23:25:07「昨晚那句"晚安"说得有点早，躺下没睡着，索性爬起来了😂」。于是 02:06 用户上线时它还醒着（"超过睡觉时间很久都没有睡觉"）。

**根因**（`offline.py` SLEEPING 兜底分支）：

```python
elif state == "SLEEPING":
    if _in_morning(now) and now >= today_wake_at(now):
        engine._do_wake()
```

兜底本意是「错过起床 cron / 电脑睡过头时补叫醒」，但**刚躺下时两条天然成立**：生活日还是当天（`_in_morning=True`）、而「今天该几点起」（08:42）早就过了 → 下一分钟就被叫醒，还顺带 `proactive("morning")` 再发一遍早安 + `flush_inbox` + `flush_missed`。

本地确定性复现（`_repro_wake.py`，拷真实库到 `.test-tmp` 后直接调 `offline.tick`）：23:25 / 23:40 两个时点都触发 `_do_wake()`。

**修法**：起床点必须**晚于入睡时刻**——睡之前那个起床点不算数。`core._do_sleep()` 落 `kv.sleep_started_at`；`offline.tick` 加 `today_wake_at(now) > start` 判断；kv 没有（部署时正睡着）退回意识流最后一条 `sleep`（新增 `db.last_stream_ts`）。

**连带后果**（一并消失）：一天两次起床/两次早安；`db.session_context` 拿「最后一条 wake」当会话起点 → 半夜假醒把当晚聊天切成两段。

### ② 无缘无故的紧急模式：撤回后窗口残留 10 分钟

`urgent_until = 2026-10-19T02:16:18` → 窗口开于 **02:06:18**，正是那条乱码消息 `1111116@5655454545454545545`（id 1240）发出的同一秒；该消息随后被撤回、**已物理删除**（意识流里留着原文得以还原）。

这串字符**不可能命中 `corpus.URGENT_QUERY`**，所以窗口只能来自网页端「我需要陪伴」勾选框（`webui.py` `data.get("urgent")`）——手机上那行 10.5px 的小字紧贴输入框，误触概率不低。而**撤回时窗口没跟着撤**，10 分钟内 TA 一直挂着【急事】语境。

**修法**：`guard.open_urgent_window(msg_id=)` 记下是谁开的窗，撤回那条消息时 `cancel_urgent_window(mid)` 一并撤销（撤回无关的 id 不动，防误撤别人的窗口）；前端勾了「我需要陪伴」发送后 toast「已开启紧急陪伴 10 分钟（撤回这条可撤销）」，误触能立刻发现。

### ③ 回复凭空消失：意识流里有，消息表里没有

意识流 `402  02:06:56  reply | 我说：睡吧，别道歉了。我这儿也合眼。` —— **这条回复生成了、也进了意识流，但 `messages` 表 1242→1244 之间一条 assistant 消息都没有**。用户 02:06:50 说「对不起，我困了，睡了」、02:06:55 说「晚安」，等到 02:08:31 追问「你咋不回我」，96 秒无人应答。

两个独立成因，叠在一起：

- **3a 插话把整条吞掉**：1242 的回复 02:06:54 生成完 → 进入打字延时（几秒）→ 02:06:55「晚安」到达 → 段循环 i=0 处的 `if self._interrupted(): break` 命中 → **一句都没发**。这条是既有设计（"打字阶段打断→整段作废"，已有用例覆盖），**不改**。
- **3b 空回复静默丢弃**：02:07:03 那一轮 LLM 返回空串（输出仅 19 token）→ `segments` 为空 → 什么都不发、什么都不记，连告警都没有。

**最糟的是 3a 的副作用**：那条没发出去的回复照样写进了意识流「我说：…」，于是 TA 以为自己回过了——02:08:37 它理直气壮答「回了啊，你自己说的困了要睡，我才没再絮叨😌」。

**修法**：①空回复退回不带独白层的原始数据重跑一次，仍空才放弃并打印 `[空回复]`；②一个字都没发出去的整条回复，**不记**「我说：…」（待办打勾/兴趣也一并跳过）——没说出口的话不算说过。

### ④ 手机端输入框：两个 CSS 缺陷

```css
.composer textarea { flex: 1; ... }      /* 缺 min-width:0 与 overflow-wrap */
```

- **缺 `min-width: 0`**：flex 项默认 `min-width:auto` 压不下去 → 长文本时整行被顶开、输入框被挤到左边。
- **缺 `overflow-wrap`**：一长串没空格的字符（乱码/长链接）在 `textarea` 里不换行 → 直接向右穿出输入框。

**修法**：`flex: 1 1 auto; min-width: 0` + `white-space: pre-wrap; overflow-wrap: break-word; word-break: break-word`。
