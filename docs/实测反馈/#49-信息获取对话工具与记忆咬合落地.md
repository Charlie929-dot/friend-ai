## 一、动手前的三轮对齐 + 一轮审查（本批方案成本最高的一次）

本批方案经**四轮**才定稿（写入方案拍板 #1–#18），其中第三轮是对照代码基线**逐行审查**（附 B，13 条），第四轮是 4 个确认点 + 2 处补充（附 C）。事后看，前几轮对齐值回票价——本批**唯一改行为**的纯规则判定（闸门 2/3）恰好是最容易写歪、也最值得先吵清楚的部分。

## 三、踩坑与实现要点（换来的教训）

### 3.1 工具可见性 vs 触发信号：默认配置下 `open_link` 只有一条可用路径（本批最根本的发现）

审查只指出"`搜一下` 族词与『本批只上 open_link』自相矛盾"；顺着往下挖，问题更根本：**默认配置（`SEARCH_PROVIDER=none`）下工具表里只有 `search_memories`/`recall_detail`/`open_link`，而 `open_link` 要一个 URL——可注入块根本不渲染 URL**（`context.py` 只给 `summary + 出处域名`，这是 §3.5 刻意的拟人约定）。

于是默认配置下：查证词、时效词触发 tool loop **都是白跑一轮**（工具表里没有能干这事的工具）；更糟的是模型可能**编一个 URL** 去调 `open_link`。

**定稿切三刀**：①② 查证 / 时效信号**与 `lookup_online` 同 gate**（没配搜索源就不算信号）；新增 ③ 类"消息里含 `https?://`"永久可用。即：**批 4 在默认配置下的用户可见价值 = "贴个链接让它看"**。

### 3.2 "永久可用"也必须挂总门（用户第四轮修正）

第 ③ 类"不受 provider 限制"很容易被读成"不受任何门"——那样 `LOOKUP_ENABLED=off` + 贴链接会**信号触发 tool loop、`specs()` 里却没有 `open_link`**，又是白跑一轮（刚 killed 的 bug 的变体）。定稿把完整形态写成**一行公式**钉在方案 §2.1，防动工时读岔：

```
(MEMORY_TOOLS_ENABLED 且 回忆信号)
或 (LOOKUP_ENABLED 且 ((SEARCH_PROVIDER != "none" 且 (查证信号 或 时效信号)) 或 消息含 https?://))
```

### 3.3 SSRF 三个必须写死的坑（不写死就会漏判）

1. **判定主机一律用 `urlparse(url).hostname`，不能复用现成的 `sources._host()`（它用 `netloc`）**——`https://ok.com@127.0.0.1/` 的 netloc 是 `ok.com@127.0.0.1`，黑名单前缀匹配会漏判，而 httpx 实际连的是 `127.0.0.1`（userinfo 绕过）。`_host()` 继续只做展示。
2. **`172.16`–`172.31` 必须用区间判定**——`startswith("172.16")` 会把公网 `172.160.x.x` 误拦。专门加了 `172.160.1.1` 应**放行**的防呆用例。
3. **重定向必须手动逐跳跟**——`follow_redirects=False` + 循环，相对 Location 先 `urljoin` 再校验，**每一跳都校验协议**（https → http 降级同拒）。测试覆盖"跳去内网被拒" + "同站相对跳转跟得上"。

### 3.4 `http://` 明文贴链：话术要贴人味（用户第四轮补充）

SSRF 的 https-only 会拒掉用户贴的明文链接，但"（这个地址我不去）"**听起来像在拒绝对方**。定稿单写一句体感话术（"这个地址走的是不加密的通道，我不开"），**就近放 `sources.py`、不进 `corpus`**（约定 #3：固定文案不属语料）。

### 3.5 闸门 2 的判据要带 `BROWSE_ENABLED` 门、位置要在失败早退之后

`context` 的注入有 `if config.BROWSE_ENABLED` 门；闸门 2 若只查 `items_today` 非空，**当天中途关掉 browse 的日子，"其实没注入"的条目也会被补进素材**。定稿判据带上同一个门，且位置放在 **LLM 失败早退（回复都没生成成功，谈不上"认真讨论过"）之后**。

### 3.6 `memory._apply()` 只返回 `bool` → 闸门 3 必须走 `db.add_long_memory()`

`memory._apply()` 只返回 bool、拿不到 `long_id`，给不了 `vecindex` 的 `ref_id`。改走 `db.add_long_memory()`（返回 id），照 `trueread.settle_chapter` 的双写先例——**顺带消灭了孤儿问题**：`ref_id` 挂的是长期记忆 id，`info_items` 90 天清理动不到它，无需任何连带清逻辑。

### 3.7 `info_items.starred` 不能拿来当"已补素材"标记

`db.py` 里 `starred` 的原语义是"预留：标记值得再看"，将来很可能被网页端「它刷到的」面板拿去做**用户加星**交互。一旦复用，"用户点星"和"已补素材"两种状态混在一个字段里，撤不回来。定稿**新加 `noted` 列**（迁移样板现成，3 行成本）——省 3 行换一个语义死结，不值。

### 3.8 `open_link` 的可见性依赖 `sources.py` 被 import（`core` 加一行 import）

工具是 `sources.py` 向 `tools` 注册的，而 `sources` 在别处都是**函数内延迟 import**。若引擎启动没 import 过它，`specs()` 里根本没有 `open_link` → 贴链接触发了 tool loop 却无工具可调。定稿在 `core.py` 顶部加 `import sources`（无循环依赖：`sources` 只 import `config/db/llm/tools` + `httpx`）。这是对"core 只加闸门 2 一个挂点"边界声明的**刻意偏离**，已记账。

## 四、已知边界（写下来防"忘了"）

- **不防 DNS rebinding**：主机名校验拦得住 `127.0.0.1` 字面量，拦不住"域名解析到内网"。自用单用户 + 正文已被摘要层隔离，风险可接受。
- **残余"编 URL"口子**：回忆信号触发的轮里 `specs()` 仍含 `open_link`，而上下文里一条合法 URL 都没有——概率低且有预算 + SSRF + 摘要层三重兜底。想从根上关有一刀**可选**（进程内"本轮见过 URL"旗），本批**不实现**。
- **`open_link` 不写 `info_cache` = 同一 URL 可反复 open**，每次 1 fetch + 1 摘要 LLM，靠预算（1/轮、20/天）兜底。
- **闸门 2 粒度粗**：`EXPAND_QUERY` 是通用追问词，只要当天注入块非空，**当天第一条"详细/具体/说说"类消息（哪怕追问的根本不是刷到的东西）就会把注入的几条整体补进素材**——量级有界（每天 ≤ `BROWSE_CONTEXT_MAX`），别在实测时当 bug 查。
- **闸门 3 盲区**：`daily_review` 在"今天还没怎么聊"时早退——**纯浏览、没对话的日子，刷到的东西永不过闸门 3，90 天后直接清掉**。符合"人味闸门"设计（没聊过 = 不重要）。
- **闸门 3 每天 ≤ 1 条**：刷到十条也只可能沉淀一条——刻意为之（保召回排序）。

## 五、「实测后再说」清单（本批刻意不做）

- **`open_browsed(哪条)`**：承载"追问刷到的某条 → TA 真能展开"的诉求。模型只说"把 Nature 那条翻开看看"，handler 自己去 `info_items` 按标题/摘要匹配、**从库里取 URL**（URL 全程不进上下文，§3.5 完好），SSRF / 预算 / 摘要管道全复用——比"往注入块塞 URL"更拟人，且是**纯加法**。**实测若发现"展开刷到的"是真需求 → 上它，不上"往注入块塞 URL"。**
- **① 类语义信号扩充**、**搜索 provider**：等配了真搜索源再补。
