# 实测反馈记录 #21（2026-10-09，Web 反馈一轮）

**背景**：网页端跑起来后，用户集中报了两条 bug + 四条建议。两条 bug 分别踩了"时间戳只有 HH:MM 分不清新旧"和"AI 从上下文脑补、静默覆盖稳定字段"两个坑；四条建议里，profile/记忆**留痕**是架构性要求。

**坑①：消息时间戳只显示 HH:MM，跨天分不清**

- 现象：所有消息只显示 `HH:MM`，昨天和今天的消息看不出区别。
- 修：今天只显 `HH:MM`；昨天显"昨天 HH:MM"；更早显 `MM-DD HH:MM`（跨年带年份）；且换天插一条居中**日期分隔条**（微信/Telegram 风格）。前端 `lastMsgDay` 记住上一条的日期，换天才插分隔条；切朋友清空聊天区时一并重置。

**坑②：AI 从上下文脑补，静默覆盖了稳定 profile 字段（本轮核心）**

- 现象：用户"一直是夜猫子"，但小葵的清单里写着"作息习惯：基本十一点多就困，偶尔刷手机拖到十二点"。用户从没说过 12 点睡。
- 根因：提取器看到某段上下文（可能是"我要睡了/晚安"之类）就脑补出"作息习惯"并**静默覆盖**——原 `_apply_profile` 里"AI 自己写过的字段就更新值"，没有任何冲突判断，也没留证据。
- 修（三层）：
  1. **留痕**：每次自动填 profile 字段，把"上下文证据"（当时对话原文）存 **B 库**（`long_memories`），**A 库那条记忆挂 `long_id` 指向证据**；`/profile` 显示 `〔证据#N〕`、`/profile why <字段>` 看原文。
  2. **稳定字段不静默覆盖**：作息/生日/城市/称呼等**身份级字段**遇到与旧值冲突的新说法，**标 `pending` 待用户确认**，不直接改（`/profile pending/accept/reject`）；可变字段（在忙的事等）照旧可更新。
  3. **有疑惑主动交流**：有 pending 时往 system prompt 注入提示，让 AI 下一条消息自然地跟用户核实"我记得你是夜猫子，怎么这次感觉睡得早了？"，而不是自己悄悄改。
- 教训：**"AI 自己写过的字段可更新"这个规则本身就是 bug 源头**——稳定字段和可变字段要分开，稳定字段的改动必须走"冲突→确认"；且任何自动写入都要留证据，否则用户没法判断 AI 是不是脑补。

**设计取舍①：证据走 A/B 库，不另起一套存储**

profile 字段的证据复用现成的 `long_memories`（B 库），A 库记忆的 `long_id` 直接指向证据——语义上就是"A 库摘要挂链接 → B 库全文"，和长文本是同一套，不额外加表。

**设计取舍②：稳定字段 / 可变字段怎么分**

`STABLE_PROFILE_FIELDS = {称呼/生日/城市/所在城市/作息习惯/职业/专业/职业-专业/学校/年级}`；其余（在忙的事/兴趣爱好/喜欢的内容类型/雷区/其他）算可变。判据：身份级、错了很伤人、极少变的 → 稳定；自然流动、常更新的 → 可变。
