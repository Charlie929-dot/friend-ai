## 3. 记忆线（B）

### M1 🔴 召回池硬上限 200 条 = 静默失忆（本线最高优先）

`memory.py:651`（recall）、`memory.py:305`（提取去重）、`memory.py:968`（random_memory）三处 `db.all_memories(limit=200)` 按 id DESC ✓——**只有最新 200 条参与召回**。本机 `friend.db` 已 223 条：最老 23 条已永久「召不回来」，之后每记一条忘一条。

落地：① 语义召回走全量向量池（M2 配套）；② 字面/标签召回窗口提大或改衰减感知（`decay_level` 低的短条目优先留在候选池——被压缩过的条目便宜）；③ 200 提为可配并进 tuning。

### M2 高：统一向量索引只落地 1/3

`event_vectors` schema 声明三源 `stream / note_beta / dialog`（`db.py:107`），全项目**唯一写入点是 `trueread.py:399`**（note_beta）✓；意识流条目、对话摘要从不进索引——「聊天想起读书、读书想起聊天」的联想闭环只通一半。`event_vectors_all(limit=2000)`（`db.py:808-814`）超量静默截断。

落地：① 每日日记时把对话摘要写进 `dialog` 源；② 意识流浓缩**前**把当天关键事件写进 `stream` 源（与 M3 purge 配对：清原文前先留向量）；③ 查询侧超量至少打日志。

### M3 高：意识流无限增长 + 双份存储

`db.purge_stream_before`（`db.py:727`）**从未被调用** ✓ → `consciousness_stream` 无限增长；reply 类「我说：…」全文入库（`core.py:235`）与 messages 表**同一内容双份存储、双份注入**。睡前浓缩进 self_ 后旧流不清理，第二天 prompt 既带浓缩产物又带全部原文。

落地：`selfmem.review` 完成后调用 `purge_stream_before` 清当天已浓缩旧流（`stream.py` docstring 本来就写了这个设计）。与 C5 配套解决 token 护栏。

### M4 中：SQLite 并发卫生

`db.py:116-119` 每次操作裸连、无 `journal_mode=WAL`、无显式 `busy_timeout`，而写方线程众多（HTTP 每请求一线程 + APScheduler + 回复/提取/judge/工作结算）。

落地：连接工厂统一 `PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000;`（多读单写场景纯收益）；再考虑线程局部连接复用（`recall` 一次现在要开 3+N 个连接）。

### E6 低：db 迁移有序化 + 锁审计开关

内联 ALTER TABLE 迁移 → 「有序迁移列表 + schema_version kv」可审计；锁审计：debug 开关让 db 写函数断言 PATH_LOCK 被持有（以后新加后台写点忘了拿锁当场抓到，不靠实测串库才发现）。实现注意：`threading.RLock` 无公开 is-owned API（`_is_owned()` 私有、CPython-only），或改日志式审计（写函数入口 debug 打印当前线程 + 是否持锁），后者更稳。

### E7 低：轻量 logging

现在是 print + journalctl；服务器端「为什么 10 点才醒」这类排查全靠 ssh 翻日志。先只给排查痛点（scheduler/work/stream）加 rotating file logging，渐进不搞全局大改。
